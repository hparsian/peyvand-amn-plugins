# به‌روزرسانی افزونه‌ها از مخزن گیت‌هاب

نسخهٔ ۲.۱۰.۰ داشبورد یکپارچه — جایگزین چرخهٔ «دانلود بسته، حذف افزونه، نصب دوباره».

## ۱. مسئله

افزونه‌های اکوسیستم در مخزن `hparsian/peyvand-amn-plugins` نگه‌داری می‌شوند و
بستهٔ آمادهٔ نصب آن‌ها در پوشهٔ `dist/` قرار می‌گیرد. تا پیش از این، هر نسخهٔ
تازه باید دستی از مخزن گرفته و روی سایت نصب می‌شد. وردپرس هم چون این افزونه‌ها
در فهرست وردپرس.اورگ نیستند، هیچ خبری از نسخه‌های تازه نداشت.

## ۲. راهکار

یک موتور بررسی آپدیت داخل خود داشبورد (`includes/class-dashboard-updater.php`)
فهرست `dist/` را از GitHub Contents API می‌خواند، نسخهٔ هر بسته را با نسخهٔ
نصب‌شده مقایسه می‌کند و نتیجه را به سه شکل در اختیار وردپرس می‌گذارد:

1. **تزریق در ترنزینت وردپرس** با هوک `pre_set_site_transient_update_plugins`؛
   نسخهٔ تازه در «پیشخوان ← به‌روزرسانی‌ها» دیده می‌شود و با همان آپ‌گریدر رسمی
   نصب می‌شود.
2. **به‌روزرسانی خودکار** با فیلتر `auto_update_plugin`؛ اگر مدیر در ماژول
   «به‌روزرسانی‌ها» فعالش کند، وردپرس نسخهٔ تازه را در پس‌زمینه نصب می‌کند.
3. **ماژول داشبورد** (`includes/modules/updates-module.php`) با جدول نسخه‌ها،
   بررسی دوباره، به‌روزرسانی تک‌تک یا همه، و تنظیمات مخزن/شاخه/توکن.

## ۳. قرارداد بستهٔ منتشرشده

هر فایل `dist/` باید این الگو را داشته باشد:

```
dist/<plugin-slug>-<version>.zip   →   <plugin-slug>/<plugin-slug>.php
```

- `<plugin-slug>` همان نام پوشهٔ افزونه در `wp-content/plugins` است.
- `<version>` عدد نقطه‌ای است (مثلاً `1.13.2.7`) و باید با هدر `Version:` فایل
  اصلی افزونه یکی باشد.
- ریشهٔ ZIP دقیقاً پوشهٔ `<plugin-slug>/` است؛ ساختار استاندارد نصب وردپرس.
- پس از هر تغییر، **نسخه را بالا ببرید**. وردپرس فقط وقتی آپدیت می‌شود که
  `version_compare(latest, installed, '>')` درست باشد؛ بازسازی بسته بدون تغییر
  نسخه، آپدیتی ایجاد نمی‌کند.

ساخت بستهٔ داشبورد (عادت همین مخزن):

```bash
cd plugins
zip -rq ../dist/peyvand-amn-unified-dashboard-<version>.zip peyvand-amn-unified-dashboard \
  -x "*.DS_Store" "*.log" "*.map"
```

## ۴. فهرست سفید

فقط افزونه‌های زیر هدف آپدیت هستند (تابع `PAS_Dashboard_Updater::plugins()`).
هیچ اسلاگ دلخواهی از مخزن یا از مرورگر نمی‌تواند پوشهٔ افزونهٔ دیگری را
بازنویسی کند:

| اسلاگ | نام |
| --- | --- |
| `peyvand-amn-unified-dashboard` | داشبورد یکپارچه |
| `pivand-amn-core` | هستهٔ مشترک |
| `pivand-amn-case-file` | پرونده‌های بالینی |
| `pivand-amn-client-portal` | پنل مراجعان |
| `pivand-amn-quiz-enterprise` | آزمون‌ها |
| `pivand-amn-sms-bridge` | پل پیامک |
| `pivand-amn-smtp-mailer` | ارسال ایمیل |
| `pivand-amn-2fa` | احراز دومرحله‌ای |
| `pivand-amn-content-writer` | تولید محتوا |
| `piwand-daily-feed` | فید روزانه |
| `payvand-contact` | فرم ارتباط |
| `payvand-amn-ui-kit` | کیت رابط |

افزودن افزونهٔ تازه یعنی افزودن یک سطر به همین تابع؛ فهرست عمداً بسته است.

## ۵. امنیت

- **HTTPS و میزبان ثابت**: بسته فقط از `github.com`، `raw.githubusercontent.com`،
  `objects.githubusercontent.com` و `codeload.github.com` پذیرفته می‌شود.
- **بدون توکن اجباری**: مخزن عمومی با ۶۰ درخواست در ساعت و کش ۶ ساعته کافی است.
- **توکن اختیاری**: برای مخزن خصوصی یا سهمیهٔ بالاتر. اولویت با ثابت
  `PAS_DASHBOARD_GITHUB_TOKEN` در `wp-config.php` است؛ در غیر این صورت از
  تنظیمات ماژول در آپشن خود داشبورد ذخیره می‌شود (متن ساده در پایگاه‌داده —
  برای همین ثابت توصیه می‌شود). توکن فقط به درخواست‌های همان مخزن افزوده
  می‌شود و هرگز در HTML، پیام یا لاگ نوشته نمی‌شود.
- **نوشتن از Action Bus**: `updates.refresh`، `updates.save` و `updates.run` با
  nonce، کپابیلیتی `manage_options`، ممیزی و POST/Redirect/GET اجرا می‌شوند.
  `updates.run` علاوه بر آن `update_plugins` و `DISALLOW_FILE_MODS` را می‌سنجد.
- **بدون بازنویسی داده**: آپدیت فقط فایل‌های همان افزونه را جایگزین می‌کند؛
  جداول و آپشن‌ها دست‌نخورده می‌مانند و هیچ جدول افزونهٔ دیگری خوانده نمی‌شود.

## ۶. آنچه کش می‌شود

| کلید | مدت | کاربرد |
| --- | --- | --- |
| `pas_dashboard_update_catalog` (site transient) | ۶ ساعت موفق / ۱۵ دقیقه خطا | فهرست بسته‌های `dist/` |
| ترنزینت `update_plugins` وردپرس | پیش‌فرض وردپرس | آپدیت‌های تزریق‌شده |

پس از هر آپدیت موفق یا تغییر تنظیمات، کش پاک می‌شود (`upgrader_process_complete`).

## ۷. رفتار در خطا

| حالت | رفتار |
| --- | --- |
| GitHub در دسترس نیست | وضعیت قبلی از کش نمایش داده می‌شود و هشدار «اتصال برقرار نشد» می‌آید؛ وردپرس دست‌نخورده می‌ماند |
| سهمیهٔ API (۴۰۳/۴۲۹) | پیام صریح برای تنظیم توکن؛ کش ۱۵ دقیقه‌ای تا سهمیه نسوزد |
| پوشهٔ `dist` نیست (۴۰۴) | پیام «نام مخزن یا شاخه را بررسی کنید» |
| افزونهٔ نصب‌شده بسته ندارد | نشان «بدون بسته در مخزن» و بدون پیشنهاد آپدیت |
| افزونه نصب نیست | نشان «نصب نشده»؛ آپدیت خودکار هرگز روی آن اجرا نمی‌شود |
| دسترسی نوشتن فایل بسته است | پیام شکست با علت از آپ‌گریدر؛ هیچ تغییری اعمال نمی‌شود |

## ۸. چک‌لیست استیجینگ

این موارد باید با وردپرس واقعی و مخزن واقعی یک‌بار آزموده شوند. گام‌های
اجرایی، دستورهای WP-CLI، بستهٔ آزمایشی و نتیجهٔ مورد انتظار هر گام در
[`GITHUB-UPDATES-STAGING-TEST.md`](GITHUB-UPDATES-STAGING-TEST.md) آمده است:

- [ ] A. باز کردن ماژول «به‌روزرسانی‌ها» با مدیر: جدول ۱۲ افزونه، نسخه‌ها و وضعیت‌ها درست است.
- [ ] B. «بررسی دوبارهٔ مخزن» → پیام موفق و به‌روز شدن زمان بررسی؛ با قطع اینترنت، پیام خطا و نمایش کش.
- [ ] C. ساخت یک بستهٔ آزمایشی با نسخهٔ بالاتر در `dist/` → دیده‌شدن در «پیشخوان ← به‌روزرسانی‌ها» و اجرای موفق آپدیت از داشبورد.
- [ ] D. فعال‌کردن «به‌روزرسانی خودکار» → اجرای `wp cron event run wp_version_check` و نصب نسخهٔ تازه در پس‌زمینه.
- [ ] E. کاربر درمانگر (بدون `manage_options`): ماژول و منو دیده نشود؛ درخواست مستقیم POST به `updates.run` با ۴۰۳ رد شود.
- [ ] F. مخزن خصوصی: توکن در تنظیمات، خواندن فهرست و دانلود بسته موفق؛ توکن در HTML و لاگ دیده نشود.
- [ ] G. ثبت ممیزی `updates.refresh` / `updates.save` / `updates.run` با وضعیت ok/error.

## ۹. محدودیت‌ها

- این سیستم بستهٔ منتشرشده در `dist/` را می‌خواند، نه سورس خام شاخه؛ آپدیت
  فقط وقتی دیده می‌شود که بستهٔ تازه کامیت شده باشد.
- امضای رمزنگاری‌شده برای بسته وجود ندارد؛ اعتماد بر HTTPS و مخزن رسمی است.
- اگر وردپرس به‌دلیل مجوز فایل یا `DISALLOW_FILE_MODS` نتواند بنویسد، آپدیت
  انجام نمی‌شود و پیام صریح نمایش داده می‌شود.
- بازبینی رابط و آزمون واقعی در این محیط ممکن نبود (PHP CLI و وردپرس اجراشدنی
  نبود)؛ فقط تحلیل ایستاتیک و بستهٔ ZIP بررسی شده است.
