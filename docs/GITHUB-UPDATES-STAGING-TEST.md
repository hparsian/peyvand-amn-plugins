# آزمون گام‌به‌گام سیستم به‌روزرسانی روی استیجینگ

این سند چک‌لیست A–G سند [`GITHUB-UPDATES.md`](GITHUB-UPDATES.md) را به گام‌های
اجرایی با «نتیجهٔ مورد انتظار» و «راه تأیید» تبدیل می‌کند. همهٔ گام‌ها روی یک
کپی استیجینگ از سایت واقعی انجام می‌شود، نه روی سایت تولید.

> **اصل کلی:** هیچ گامی نباید حالت سایت را تغییر دهد مگر همان چیزی که آزمون
> می‌سنجد. آزمون آپدیت فقط با یک بستهٔ آزمایشی در یک شاخهٔ موقت انجام می‌شود و
> در پایان همان شاخه و بسته پاک می‌شود؛ بستهٔ آزمایشی هرگز به `main` نمی‌رود.

## ۰. پیش‌نیازها

| مورد | مقدار لازم |
| --- | --- |
| وردپرس | ۵.۸ یا بالاتر، PHP ۷.۴ یا بالاتر |
| افزونهٔ داشبورد | بستهٔ `dist/peyvand-amn-unified-dashboard-2.10.0.zip` نصب و فعال |
| دسترسی | یک کاربر مدیر (`manage_options`) و یک کاربر درمانگر بدون آن |
| WP-CLI | برای اجرای کرون، خواندن آپشن و پرس‌وجوی ممیزی |
| سایت | دسترسی نوشتن به `wp-content/plugins` (نه `DISALLOW_FILE_MODS`) |

قبل از شروع:

```bash
# پشتیبان پایگاه‌داده و پوشهٔ افزونه‌ها
wp db export staging-before-updates-test.sql
tar -czf plugins-before-updates-test.tar.gz wp-content/plugins

# نصب بستهٔ داشبورد
wp plugin install /path/to/dist/peyvand-amn-unified-dashboard-2.10.0.zip --force --activate
wp plugin get peyvand-amn-unified-dashboard --field=version
```

**نتیجهٔ مورد انتظار:** دستور آخر `2.10.0` را چاپ می‌کند؛ در «افزونه‌ها» هیچ
خطای فعال‌سازی نیست و در فهرست افزونه‌ها گروه منوی «داشبورد یکپارچه» با آیتم
«به‌روزرسانی‌ها» دیده می‌شود.

## ۱. باز کردن ماژول با مدیر (چک‌لیست A)

به «داشبورد یکپارچه ← به‌روزرسانی‌ها» بروید، یا مستقیم:

```
/wp-admin/admin.php?page=pas-unified-dashboard&module=updates
```

**نتیجهٔ مورد انتظار:**

- کارت «خلاصهٔ به‌روزرسانی» چهار عدد نشان می‌دهد: افزونهٔ اکوسیستم (۱۲)،
  به‌روزرسانی موجود، به‌روز، نصب‌نشده.
- زیر آن «مخزن: hparsian/peyvand-amn-plugins — شاخه: main» و جملهٔ کش ۶ ساعته.
- جدول «وضعیت نسخه‌ها» ۱۲ سطر دارد (یا هر تعداد از فهرست سفید که نصب شده‌اند
  هم نمایش داده می‌شوند) با ستون‌های افزونه، نسخهٔ نصب‌شده، آخرین نسخهٔ مخزن،
  وضعیت، جزئیات، عملیات.
- نشان هر سطر یکی از این‌هاست: **به‌روز**، **به‌روزرسانی موجود**، **نصب نشده**،
  **بدون بسته در مخزن**، **نامشخص**.
- دکمه‌های «بررسی دوبارهٔ مخزن»، و اگر آپدیتی هست «به‌روزرسانی همهٔ افزونه‌ها»،
  و کارت «تنظیمات مخزن» دیده می‌شوند.

**راه تأیید:** نسخهٔ ستون «نسخهٔ نصب‌شده» را با خروجی زیر مقایسه کنید؛ باید
یکی باشند:

```bash
wp plugin list --fields=name,version,status --format=table
```

اگر همهٔ سطرها «نامشخص» بودند، یعنی خواندن فهرست مخزن شکست خورده است؛ به
گام ۹ بروید و علت را از پیام هشدار بالای جدول بخوانید.

## ۲. بررسی دوباره، کش و قطع اتصال (چک‌لیست B)

۱. دکمهٔ «بررسی دوبارهٔ مخزن» را بزنید.
۲. سپس کش را دستی حذف کنید و صفحه را دوباره باز کنید:

```bash
wp transient delete pas_dashboard_update_catalog --network   # اگر چندسایتی است
wp transient delete pas_dashboard_update_catalog
wp transient list --search=pas_dashboard_update
```

**نتیجهٔ مورد انتظار گام ۱:** پیام سبز با این شکل:
«فهرست مخزن به‌روز شد: N به‌روزرسانی در دسترس، ۱۲ بسته در مخزن.»
صفحه با POST/Redirect/GET برمی‌گردد (یعنی آدرس پایانی همان ماژول است و با
رفرش دوباره عملی اجرا نمی‌شود).

**آزمون خطا:** در شبکهٔ استیجینگ دسترسی خروجی به `api.github.com` را موقتاً
ببندید (یا در `functions.php` استیجینگ یک `pre_http_request` موقت بگذارید که
برای همین میزبان `WP_Error` برگرداند) و دوباره «بررسی دوبارهٔ مخزن» را بزنید.

**نتیجهٔ مورد انتظار خطا:**

- پیام قرمز: «اتصال به گیت‌هاب برقرار نشد؛ آخرین وضعیت کش‌شده نمایش داده
  می‌شود.»
- جدول همان نسخه‌های کش قبلی را نشان می‌دهد، نه سطر خالی.
- کش خطا ۱۵ دقیقه زنده می‌ماند (`FAILURE_TTL`)، پس درخواست پشت‌سرهم سهمیه
  نمی‌سوزاند:

```bash
wp transient get pas_dashboard_update_catalog --format=json | head -c 300
```

**راه تأیید:** تا وقتی بلاک فعال است، هیچ درخواست تازه‌ای به گیت‌هاب نمی‌رود
(می‌توانید در لاگ پراکسی بشمارید)؛ پس از رفع بلاک و یک «بررسی دوباره»، فهرست
تازه برمی‌گردد.

## ۳. ساخت بستهٔ آزمایشی نسخه‌بالاتر (چک‌لیست C)

برای اینکه آزمون، سایت واقعی را دست‌کاری نکند، از یک شاخهٔ موقت استفاده کنید.

```bash
# در یک کلون از مخزن
git checkout -b updates-test

# نسخهٔ یک افزونهٔ کم‌ریسک را یک پچ بالا ببرید، مثلاً پل پیامک
# (هدر Version و ثابت نسخه، هر دو)
grep -rn "1\.1\.10" plugins/pivand-amn-sms-bridge | head

# پس از تغییر نسخه به 1.1.11، بسته را بسازید
cd plugins
zip -rq ../dist/pivand-amn-sms-bridge-1.1.11.zip pivand-amn-sms-bridge \
  -x "*.DS_Store" "*.log" "*.map"
cd ..
unzip -p dist/pivand-amn-sms-bridge-1.1.11.zip \
  pivand-amn-sms-bridge/pivand-amn-sms-bridge.php | grep -m1 "Version:"

git add plugins/pivand-amn-sms-bridge dist/pivand-amn-sms-bridge-1.1.11.zip
git commit -m "test: staging update package (do not merge)"
git push origin updates-test
```

سپس در ماژول «به‌روزرسانی‌ها»، در کارت «تنظیمات مخزن»، شاخه را `updates-test`
کنید و ذخیره بزنید.

**نتیجهٔ مورد انتظار پس از ذخیره:**

- پیام سبز «تنظیمات به‌روزرسانی ذخیره شد؛ فهرست مخزن دوباره خوانده می‌شود.»
- سطر آن افزونه نشان **به‌روزرسانی موجود** با نسخهٔ نصب‌شدهٔ `1.1.10` و آخرین
  نسخهٔ `1.1.11` و دکمهٔ «به‌روزرسانی» در ستون عملیات.
- در «پیشخوان ← به‌روزرسانی‌ها» نیز همان افزونه با نسخهٔ `1.1.11` دیده می‌شود؛
  این همان تزریق در ترنزینت `update_plugins` است.

**راه تأیید تزریق، بدون مرورگر:**

```bash
wp transient delete update_plugins
wp eval 'wp_update_plugins(); $t = get_site_transient("update_plugins"); echo isset($t->response["pivand-amn-sms-bridge/pivand-amn-sms-bridge.php"]) ? "injected: ".$t->response["pivand-amn-sms-bridge/pivand-amn-sms-bridge.php"]->new_version : "not injected";'
```

باید `injected: 1.1.11` چاپ شود.

> اگر «به‌روزرسانی موجود» دیده نشد ولی بسته در مخزن هست، اولین احتمال این است
> که هدر `Version:` داخل ZIP بالا نرفته است؛ وردپرس فقط با
> `version_compare(latest, installed, '>')` آپدیت می‌شمارد.

## ۴. اجرای آپ‌گریدر از داشبورد (چک‌لیست C، ادامه)

۱. دکمهٔ «به‌روزرسانی» روی همان سطر را بزنید (نه «همه»).
۲. پس از بازگشت صفحه، نسخه و فایل‌ها را بررسی کنید.

**نتیجهٔ مورد انتظار:**

- پیام سبز: «۱ افزونه از مخزن گیت‌هاب به‌روز شد.»
- نسخهٔ ستون «نسخهٔ نصب‌شده» به `1.1.11` رسیده و وضعیت **به‌روز** شده است.
- در پیشخوان، شمارندهٔ آپدیت‌ها یک عدد کم شده است.
- کش فهرست پاک شده و در درخواست بعدی دوباره خوانده می‌شود
  (`upgrader_process_complete`).

**راه تأیید:**

```bash
wp plugin get pivand-amn-sms-bridge --field=version      # → 1.1.11
wp plugin list --fields=name,version,status | grep sms
mysql -e "SELECT action,object_type,result,created_at FROM $(wp db prefix)pas_dashboard_audit ORDER BY id DESC LIMIT 5;"
```

**حالت‌های شکست که باید ببینید (نه سبز شدن):**

| سناریو | نتیجهٔ مورد انتظار |
| --- | --- |
| `wp-config.php` را با `DISALLOW_FILE_MODS true` اجرا کنید | پیام «نصب و تغییر فایل‌ها در این سایت غیرفعال است (DISALLOW_FILE_MODS).» و هیچ تغییری در فایل‌ها |
| پوشهٔ افزونه را فقط‌خواندنی کنید (`chmod -R a-w`) | پیام «به‌روزرسانی ۱ افزونه انجام نشد؛ دسترسی نوشتن فایل یا اتصال به گیت‌هاب را بررسی کنید.» + علت آپ‌گریدر |
| بدون هیچ آپدیت واقعی، `updates.run` را با slug ناموجود صدا بزنید | پیام «هیچ به‌روزرسانی‌ای برای اجرا وجود ندارد؛ ابتدا مخزن را بررسی کنید.» |

پس از هر شکست، نسخهٔ افزونه نباید تغییر کرده باشد.

## ۵. به‌روزرسانی خودکار در پس‌زمینه (چک‌لیست D)

۱. در کارت «تنظیمات مخزن»، تیک «به‌روزرسانی خودکار افزونه‌های همین فهرست در
   پس‌زمینه» را بزنید و ذخیره کنید.
۲. یک بستهٔ آزمایشی دیگر با نسخهٔ بالاتر بسازید (`1.1.12`) و در شاخهٔ
   `updates-test` بگذارید.
۳. بروزرسانی خودکار وردپرس را با کرون شبیه‌سازی کنید:

```bash
wp option get pas_dashboard_settings --format=json | grep enable_auto_updates   # باید true باشد
wp transient delete update_plugins
wp transient delete pas_dashboard_update_catalog
wp cron event run wp_version_check
sleep 10
wp plugin get pivand-amn-sms-bridge --field=version
```

اگر آپدیت خودکار انجام نشد، اجرای مستقیم زمان‌بند پس‌زمینه را امتحان کنید:

```bash
wp eval 'if ( function_exists("wp_maybe_auto_update") ) { wp_maybe_auto_update(); } else { echo "wp_maybe_auto_update unavailable"; }'
wp plugin get pivand-amn-sms-bridge --field=version
```

**نتیجهٔ مورد انتظار:** نسخه به `1.1.12` می‌رسد، بدون هیچ کلیک در پیشخوان.

**آزمون منفی (مهم):** یک افزونهٔ نصب‌شدهٔ **بیرون** از فهرست سفید را با نسخهٔ
قدیمی نگه دارید و همین کرون را اجرا کنید.

**نتیجهٔ مورد انتظار منفی:** آن افزونه به‌روز نمی‌شود؛ فیلتر
`auto_update_plugin` فقط فایل‌های `PAS_Dashboard_Updater::plugins()` را
`true` می‌کند و برای بقیه مقدار ورودی را دست‌نخورده برمی‌گرداند. این را با
خروجی زیر تأیید کنید:

```bash
wp eval '$f = "some-other-plugin/some-other-plugin.php"; var_export( apply_filters("auto_update_plugin", false, (object) array("plugin" => $f, "slug" => "some-other-plugin")) );'
# باید false چاپ شود
```

> نکته: ذخیرهٔ فرم بدون تیک، یعنی خاموش‌کردن به‌روزرسانی خودکار؛ مقدار فقط از
> `enable_auto_updates` در همان POST خوانده می‌شود.

## ۶. مخزن خصوصی و توکن (چک‌لیست F)

**۶الف — توکن از `wp-config.php` (روش توصیه‌شده):**

```php
define( 'PAS_DASHBOARD_GITHUB_TOKEN', 'ghp_xxxxxxxxxxxxxxxx' );
```

سپس در ماژول، کارت تنظیمات باید جملهٔ «توکن از ثابت
PAS_DASHBOARD_GITHUB_TOKEN در wp-config.php خوانده می‌شود.» را نشان دهد و
فیلد توکن و تیک «توکن ذخیره‌شده پاک شود» نباید دیده شوند.

**۶ب — توکن از تنظیمات ماژول:** فیلد «توکن گیت‌هاب (اختیاری)» را پر کنید و
ذخیره بزنید. بعد از ذخیره، فیلد باید خالی باشد و فقط نگه‌دارندهٔ `••••••••`
دیده شود؛ فیلد `type="password"` با `value=""` است و مقدار هرگز بازنویسی
نمی‌شود.

**۶ج — بررسی واقعی:**

```bash
# خواندن فهرست dist با توکن (باید ۲۰۰ بدهد)
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Authorization: Bearer $GITHUB_TOKEN" \
  -H "Accept: application/vnd.github+json" \
  https://api.github.com/repos/<owner>/<private-repo>/contents/dist

# تنظیم مخزن خصوصی در ماژول و سپس «بررسی دوباره»
```

**نتیجهٔ مورد انتظار:** پیام سبز بررسی، نمایش نسخه‌های مخزن خصوصی، و اجرای
موفق آپدیت از همان مخزن (دانلود بسته هم توکن می‌گیرد، چون
`http_request_args` آن را فقط برای `raw.githubusercontent.com/<repo>/` و
`api.github.com/repos/<repo>` و `github.com/<repo>/` اضافه می‌کند).

**آزمون نشت توکن (باید همه خالی باشند):**

```bash
# ۱) HTML صفحهٔ ماژول
curl -s -b "$COOKIE" "https://staging.example.com/wp-admin/admin.php?page=pas-unified-dashboard&module=updates" \
  | grep -Eio "ghp_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]+" | head

# ۲) لاگ دیباگ
grep -Eio "ghp_[A-Za-z0-9]{20,}|github_pat_[A-Za-z0-9_]+" wp-content/debug.log | head

# ۳) رشتهٔ توکن نباید در پاسخ هیچ درخواستی باشد
grep -c "Authorization" wp-content/debug.log   # فقط اگر لاگ درخواست‌ها فعال است
```

**نتیجهٔ مورد انتظار:** هر سه دستور هیچ خروجی‌ای نمی‌دهند. اگر توکن در HTML
دیده شد، آزمون شکست خورده است — متوقف شوید و گزارش دهید.

**آزمون منفی توکن:** کاربر درمانگر نباید کارت تنظیمات را ببیند و نباید بتواند
`updates.save` را اجرا کند (گام ۷).

## ۷. کنترل دسترسی (چک‌لیست E)

با کاربر درمانگر (بدون `manage_options`):

۱. به آدرس ماژول مستقیم بروید.
۲. یک POST دستی به `updates.run` بزنید (با nonce معتبر همان کاربر، اگر داشت).
۳. یک POST بدون nonce بزنید.
۴. همان POST را با متد GET بزنید.

**نتیجهٔ مورد انتظار:**

| آزمون | پاسخ | پیام |
| --- | --- | --- |
| باز کردن `module=updates` | منو و ماژول دیده نمی‌شود؛ دسترسی به داشبورد رد می‌شود یا ماژول در ناوبری نیست | — |
| POST `updates.run` با nonce کاربر درمانگر | `403` | «دسترسی به این عملیات مجاز نیست.» |
| POST بدون `_pasnonce` | `403` | «توکن امنیتی نامعتبر یا منقضی شده است.» |
| GET روی `admin-post.php?action=pas_dash_action&pas_action=updates.run` | `405` | «این عملیات فقط با POST مجاز است.» |

**راه تأیید نمودن رد شدن:** در ممیزی، رخداد `updates.run` با نتیجهٔ `denied`
ثبت می‌شود (بدون اجرای آپ‌گریدر). و هیچ فایلی تغییر نمی‌کند.

نمونهٔ POST دستی برای مدیر (برای اینکه ببینید مسیر عادی کار می‌کند):

```bash
# nonce را از فرم صفحه بگیرید
NONCE=$(curl -s -b "$COOKIE" "$MODULE_URL" | grep -o 'name="_pasnonce" value="[^"]*"' | head -1 | sed 's/.*value="//;s/"//')
curl -s -o /dev/null -w "%{http_code} %{redirect_url}\n" -b "$COOKIE" \
  -X POST "https://staging.example.com/wp-admin/admin-post.php" \
  --data-urlencode "action=pas_dash_action" \
  --data-urlencode "pas_action=updates.run" \
  --data-urlencode "_pasnonce=$NONCE" \
  --data-urlencode "_pas_redirect=$MODULE_URL" \
  --data-urlencode "slug="
```

**نتیجهٔ مورد انتظار:** `302` با مقصد همان ماژول (POST/Redirect/GET)، و پس از
باز شدن مقصد، پیام فلش نتیجهٔ عملیات.

## ۸. ممیزی (چک‌لیست G)

پس از گام‌های ۲ تا ۶، سه اکشن باید در جدول ممیزی دیده شوند:

```bash
mysql -e "SELECT id, action, object_type, result, created_at
          FROM $(wp db prefix)pas_dashboard_audit
          WHERE action LIKE 'updates.%'
          ORDER BY id DESC LIMIT 20;"
```

**نتیجهٔ مورد انتظار:**

| رخداد | `object_type` | `result` |
| --- | --- | --- |
| `updates.refresh` | `updates` | `ok` (یا `error` در گام قطع اتصال) |
| `updates.save` | `settings` | `ok` |
| `updates.run` | `plugin` | `ok` پس از آپدیت موفق، `error` پس از شکست نوشتن، `denied` برای رد دسترسی |

**راه تأیید تکمیلی:** در ماژول «ممیزی» داشبورد همین رخدادها با زمان و کاربر
دیده می‌شوند. هیچ توکن، مسیر فایل یا محتوای بسته در ممیزی ثبت نمی‌شود.

## ۹. حالت‌های خطا و سهمیهٔ API

| تنظیم عمدی | نتیجهٔ مورد انتظار |
| --- | --- |
| شاخه را `does-not-exist` بگذارید | پیام «پوشهٔ dist در مخزن پیدا نشد؛ نام مخزن یا شاخه را در تنظیمات بررسی کنید.» و کش ۱۵ دقیقه‌ای |
| مخزن را به مخزن عمومی بدون `dist` تغییر دهید | همان پیام ۴۰۴؛ هیچ سطر آپدیتی تزریق نمی‌شود |
| بدون توکن، بررسی پشت‌سرهم تا تمام‌شدن سهمیه | پیام «سهمیهٔ GitHub API تمام شده است. برای بررسی خودکار بدون وقفه، توکن گیت‌هاب را تنظیم کنید.» و کش ۱۵ دقیقه‌ای |
| نام مخزن نامعتبر مثل `not a repo` | ذخیره رد می‌شود: «نام مخزن باید به شکل owner/repository باشد؛ چیزی ذخیره نشد.» |

**راه تأیید:** در همهٔ این حالت‌ها صفحهٔ «افزونه‌ها» دست‌نخورده می‌ماند و
هیچ آپدیتی از منبع ناشناس پیشنهاد نمی‌شود؛ بسته‌ای که میزبانش گیت‌هاب نباشد
(مثلاً CDN دلخواه) در فهرست اصلاً پذیرفته نمی‌شود
(`is_allowed_package_url`).

## ۱۰. پاک‌سازی پس از آزمون

```bash
# ۱) شاخه را به main برگردانید
#    ماژول ← تنظیمات مخزن ← شاخه: main ← ذخیره

# ۲) افزونهٔ آزمایشی را به نسخهٔ منتشرشده برگردانید
wp plugin install /path/to/dist/pivand-amn-sms-bridge-1.1.10.zip --force --activate

# ۳) بسته و شاخهٔ آزمایشی را پاک کنید
git push origin --delete updates-test
git branch -D updates-test
# فایل dist/pivand-amn-sms-bridge-1.1.11.zip و 1.1.12.zip را حذف کنید

# ۴) توکن آزمایشی را پاک کنید
#    wp-config.php ← حذف ثابت، یا تیک «توکن ذخیره‌شده پاک شود» در ماژول

# ۵) کش‌ها
wp transient delete pas_dashboard_update_catalog
wp transient delete update_plugins

# ۶) اگر بستهٔ آزمایشی روی main رفت، آن را برگردانید
git log --oneline origin/main -3
```

**نتیجهٔ مورد انتظار:** نسخهٔ همهٔ افزونه‌ها همان نسخهٔ منتشرشده است، ماژول
روی شاخهٔ `main` است، ستون «آخرین نسخهٔ مخزن» با «نسخهٔ نصب‌شده» هم‌سو است و
هیچ فایل آزمونی در `dist/` نمانده است.

## ۱۱. معیار پذیرش

سیستم وقتی «آزموده‌شده» شمرده می‌شود که همهٔ موارد زیر یک‌جا برقرار باشند:

- [ ] جدول ۱۲ افزونه با نسخه‌های درست و پنج وضعیت ممکن نمایش داده می‌شود.
- [ ] آپدیت در «پیشخوان ← به‌روزرسانی‌ها» دیده می‌شود، نه فقط در داشبورد.
- [ ] اجرای آپدیت از داشبورد نسخه را واقعاً بالا می‌برد و کش را پاک می‌کند.
- [ ] به‌روزرسانی خودکار فقط روی فهرست سفید اثر دارد.
- [ ] توکن در HTML، لاگ و ممیزی دیده نمی‌شود و مخزن خصوصی کار می‌کند.
- [ ] درمانگر هیچ‌یک از سه اکشن را اجرا نمی‌کند و رد شدنش ممیزی می‌شود.
- [ ] حالت‌های ۴۰۳/۴۰۴/خطای شبکه پیام صریح می‌دهند و سایت را تغییر نمی‌دهند.

هر بندی که رد شد، به‌عنوان «آزمون ناموفق» با خروجی دقیق ثبت شود؛ نه با
تفسیر. اگر بندی به‌دلیل نبود دسترسی (مثلاً مخزن خصوصی در دسترس نبود) اجرا
نشد، صریحاً «اجرا نشد» نوشته شود، نه «قبول».
