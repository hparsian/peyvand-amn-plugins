## ۲. آزمون نفوذ منطقی بین نقش‌ها (درمانگر / مدیر / مراجع)

نقش‌های آزمون: `administrator`، دو درمانگر مستقل (`pas_cf_therapist`) و یک مراجع (`subscriber`).
هر درخواست با کوکی نشست همان کاربر و nonce معتبر خودش زده شد (نه nonce ادمین).

| تلاش | انتظار | نتیجه |
|---|---|---|
| درمانگر A → صفحهٔ پروندهٔ درمانگر B | رد + بدون نشت نام/یادداشت | **PASS** (۲۰۰ با پیام «تخصیص داده نشده»، `leak=no`) |
| درمانگر A → پروندهٔ خودش (کنترل مثبت) | باز شود | **PASS** |
| درمانگر A → فهرست پرونده‌ها | فقط پرونده‌های خودش | **PASS** (`http=403` برای دامنهٔ دیگران) |
| درمانگر A → چاپ پروندهٔ B | رد | **PASS** (`403`، بدون نشت) |
| درمانگر A → حذف یادداشت پروندهٔ B | رد و یادداشت باقی بماند | **PASS** (`403`، `note_survived=yes`) |
| درمانگر A → ذخیره/تغییر نام پروندهٔ B | رد | **PASS** (`403`، نام دست‌نخورده) |
| درمانگر A → خروجی CSV | فقط پرونده‌های خودش | **PASS** (بدون نام پروندهٔ B) |
| درمانگر A → داشبورد سلامت/تنظیمات پیامک/مدیریت پرتال | `403` | **PASS** (۳ مورد) |
| ادمین → پروندهٔ هر دو درمانگر (کنترل) | دسترسی | **PASS** |
| مراجع → پرونده‌ها و فهرست | رد | **PASS** (`403/403`) |
| مراجع → حذف یادداشت / ذخیرهٔ پرونده | رد و داده سالم | **PASS** |
| بدون ورود → صفحهٔ پرونده | رد | **PASS** (`302`) |
| درمانگر → گزارش آزمون (`/psy/v1/report/{id}`) بدون توکن | `401/403` | **PASS** (`401 rest_forbidden`) |

**تنها مورد ACCEPTED (ریسک پذیرفته‌شده، نه باگ):** اکشن `pas_core_lookup_client_name`
برای درمانگر لاگین‌شده نام مراجع را از روی شماره برمی‌گرداند (پاسخ: فقط نام، بدون دادهٔ
بالینی). این یک قابلیت عمدی برای جلوگیری از ثبت تکراری پرونده است و nonce اجباری دارد
(بدون nonce → `403/-1`). اگر سیاست «کمترین دسترسی» سخت‌گیرانه‌تر خواسته شود، محدود کردن
این اکشن به پرونده‌های تخصیص‌یافته یک تغییر کوچک است (ریسک R-۳ در بخش ۹).

## ۳. آزمون واقعی MySQL

- MySQL/MariaDB واقعی با `mysqli`؛ هیچ drop-in یا شبیه‌سازی SQLite در مسیر آزمون نبود.
- سناریوی سرتاسری ۱۷ گامی اکوسیستم (رزرو، نگاشت پرونده، رمزنگاری، آزمون، نمای زوجی،
  یادآور، مرز دسترسی، 2FA) روی همین دیتابیس: **۱۷/۱۷ PASS** و `wpdb last_error: none`.
- SQL mode سرور: `STRICT_TRANS_TABLES,ERROR_FOR_DIVISION_BY_ZERO,NO_AUTO_CREATE_USER,NO_ENGINE_SUBSTITUTION`
  — یعنی آزمون‌ها زیر حالت سخت‌گیرانهٔ MySQL اجرا شدند، نه حالت آسان‌گیر.

## ۴. آزمون بازیابی بکاپ

روش: `mariadb-dump --single-transaction --routines --triggers` → دیتابیس تازه → import →
مقایسهٔ ساختار و داده → رمزگشایی یک رکورد بالینی از دیتابیس بازیابی‌شده با فایل کلید سایت.

| بررسی | نتیجه |
|---|---|
| جدول‌ها | ۳۷ در مبدأ، ۳۷ در بازیابی، `diff=0` |
| شمارش ردیف همهٔ جدول‌ها | `row_count_mismatches=0` |
| `CHECKSUM TABLE` (پرونده‌ها، یادداشت‌ها، لاگ ممیزی) | هر سه جفت یکسان |
| جست‌وجوی متن سادهٔ بالینی در فایل dump | `plaintext_hits=0` |
| رمزگشایی ciphertext از دیتابیس بازیابی‌شده | `OK` |
| همان داده بدون فایل کلید | `cannot_decrypt` (اثبات جدا بودن کلید از بکاپ) |

**نتیجهٔ عملیاتی:** بکاپ دیتابیس به‌تنهایی برای بازیابی کامل کافی **نیست**؛ فایل کلید
(`wp-content/pas-encryption-key.php`) باید جداگانه بکاپ گرفته شود، وگرنه دادهٔ بالینی
برای همیشه غیرقابل خواندن می‌ماند. این نکته در چک‌لیست انتشار (بخش ۱۰) آمده است.

بازتولید: `PHP_BIN=... bash tests/phase11/backup-restore.sh wp_phase11 wp_phase11_rs`

## ۷. پیامک و OTP

**مسیر افزونه (واقعی، بدون ارسال به گوشی):** ترنسپورت شبکه با فیلتر `pre_http_request`
شبیه‌سازی شد تا هیچ پیامکی ارسال نشود، ولی همان کد افزونه اجرا شود. نتایج (۱۳/۱۳ PASS):

| بررسی | نتیجه |
|---|---|
| `POST /zdp/v1/send-otp` | ۲۰۰ + «کد تایید ارسال شد» |
| payload درخواست به ملی‌پیامک | `to` = شمارهٔ کاربر، `bodyId` = کد پترن، `text` = همان کدی که ذخیره شده، نام‌کاربری از تنظیمات، رمز از دیتابیس رمزنگاری‌شده |
| کد اشتباه | ۴۰۰ + شمارش تلاش باقی‌مانده |
| کد درست | ۲۰۰ و ورود مراجع (redirect با توکن) |
| ارسال مجدد زیر ۶۰ ثانیه | ۴۰۰ (محدودیت نرخ) |
| کد منقضی‌شده | ۴۰۰ + پیام «منقضی شده یا قبلاً استفاده شده» |
| ۵ تلاش ناموفق | قفل + حذف کد از انبار، حتی کد درست دیگر پذیرفته نمی‌شود |
| شکست ارسال | ۴۰۰ + پیام شفاف، **هیچ کد یتیمی ذخیره نمی‌شود**، خطا در `pas_sms_log` ثبت می‌شود |

**آزمون واقعی بیرونی (بدون شبیه‌سازی):** یک درخواست واقعی به
`rest.payamak-panel.com` با اعتبارنامهٔ ساختگی زده شد. پاسخ واقعی سرویس
`RetStatus=35` («پترن یافت نشد یا تایید نشده است») بود و افزونه آن را درست به خطای
کاربری + ردیف لاگ ناموفق تبدیل کرد — یعنی قالب درخواست و تفسیر پاسخ سرویس واقعی
درست است (این همان باگی است که نسخه‌های قدیمی داشتند: خطای منطقی را «موفق» می‌گرفتند).

**BLOCKED:** «رسیدن پیامک به گوشی واقعی» قابل اثبات نیست، چون در این محیط هیچ
اعتبارنامهٔ معتبر ملی‌پیامک و هیچ شمارهٔ واقعی وجود ندارد. برای بستن این مورد:
روی staging با اعتبارنامهٔ واقعی، یک شمارهٔ آزمایشی و کد پترن تأییدشده اجرا شود
(`tests/phase11/sms-otp.sh` بدون شبیه‌سازی، فقط بخش ۱).

| R-۲ | ارسال واقعی پیامک/OTP روی گوشی تأییدنشده | متوسط | BLOCKED در این محیط؛ باید پیش از انتشار روی staging با اعتبارنامهٔ واقعی تأیید شود |
| R-۳ | جست‌وجوی نام مراجع برای هر درمانگر لاگین‌شده (ACCEPTED) | پایین | فقط نام، با nonce؛ در صورت سیاست سخت‌گیرانه به پرونده‌های تخصیص‌یافته محدود شود |
| R-۴ | آزمون مرورگری/UI با مرورگر واقعی انجام نشد | پایین | همهٔ آزمون‌های دسترسی با HTTP + کوکی واقعی انجام شد؛ کلیک‌های UI تأییدنشده |
| R-۵ | اجرای WPCS در این محیط ممکن نشد (ناسازگاری phpcs 4 با WPCS) | پایین | بررسی نحوی PHP برای همهٔ فایل‌های تغییریافته انجام شد؛ WPCS باید در CI پروژه اجرا شود |
| R-۶ | گزارش‌ها/CSV/پرینت شامل دادهٔ شناسایی مراجع‌اند | متوسط | دسترسی محدود به نقش‌های مجاز + لاگ ممیزی؛ سیاست نگهداری/اشتراک‌گذاری فایل باید آموزش داده شود |

## ۱۱. آمادگی انتشار

**آمادهٔ انتشار مشروط (Release-ready with conditions).** شرایط پیش از انتشار روی سایت واقعی:

- [ ] ارسال واقعی یک OTP با اعتبارنامهٔ معتبر (R-۲).
- [ ] بکاپ **هم‌زمان** دیتابیس و `pas-encryption-key.php` و تست بازیابی روی همان بکاپ (R-۱).
- [ ] نصب بسته‌های `dist/` از مسیر «افزودن افزونه → بارگذاری» (نه جایگزینی دستی پوشه) و
      باز کردن یک‌بارهٔ هر صفحهٔ ادمین (اجرای روتین‌های ارتقا).
- [ ] بعد از ارتقا: باز کردن یک پروندهٔ قدیمی و دیدن یک یادداشت قدیمی (تأیید رمزگشایی در محیط واقعی).
- [ ] فعال بودن `WP_DEBUG` در staging و خالی بودن `debug.log` از Fatal/Warning.
- [ ] اجرای WPCS در CI (R-۵).

هیچ‌کدام از این شرایط نیازمند تغییر کد نیست؛ همه «تأیید محیط واقعی» هستند.
