# فاز ۶ — جلسهٔ مشترک و نمای زوجی

تاریخ: ۲۰ آبان ۱۴۰۵ (2026-11-11)
وضعیت: پیاده‌سازی‌شده — **تأیید نحوی انجام شد؛ اجرای زنده در وردشپ انجام نشده**

## ۱. دامنه

دو پروندهٔ لینک‌شده (پارتنر/همسر) تا حالا فقط یک بنر و لینک داشتند؛ درمانگر
نمی‌توانست ببیند جلسه‌های دو طرف چه ترتیبی دارند و کدام جلسه مشترک بوده.
این فاز:

1. **پرچم جلسهٔ مشترک** روی خود جلسه.
2. **نمای زمانی زوجی** که جلسه‌های هر دو پرونده را کنار هم نشان می‌دهد —
   فقط زمان‌بندی/وضعیت، **نه متن یادداشت**.

## ۲. تغییرات — `pivand-amn-case-file` 1.13.0 → **1.14.0**

### ستون جدید (افزایشی)

`pas_cf_notes.is_joint tinyint(1) NOT NULL DEFAULT 0` — dbDelta روی جدول موجود
اضافه می‌کند؛ همهٔ جلسه‌های قبلی «غیرمشترک» می‌مانند.

### متادیتا

- `session_meta_columns()` کلید `is_joint` را می‌پذیرد.
- `add_note`/`update_note` همان الگوی `null = دست نزن` را دارند.
- فرم ثبت و ویرایش جلسه: تیک «جلسهٔ مشترک (حضور هر دو نفر)» و نشان
  «🤝 جلسهٔ مشترک» روی کارت.

### `get_couple_sessions($case, $limit = 60)`

خروجی:

```php
[
  'partner'          => object|null,   // پروندهٔ پارتنر (اگر لینک باشد)
  'can_view_partner' => bool,          // آیا کاربر به پروندهٔ پارتنر دسترسی دارد
  'sessions'         => [ ['side' => 'self|partner', 'date', 'number', 'status',
                            'duration', 'is_joint', 'author_id'], ... ],
]
```

- کوئری روی `pas_cf_notes` با `case_id IN (خود، پارتنر)` و فقط وقتی پروندهٔ
  پارتنر هم برای همین کاربر مجاز باشد.
- ستون‌های برگشتی عمداً **بدون** `content_encrypted` هستند؛ این نمای مشترک
  هیچ متن بالینی نمی‌خواند و رمزگشایی نمی‌کند.
- اگر لینک وجود داشته باشد ولی دسترسی نباشد: فقط جلسه‌های خودِ پرونده +
  `can_view_partner=false`؛ UI پیام محرمانگی نشان می‌دهد و هیچ شمارشی از
  جلسه‌های طرف مقابل لو نمی‌رود.
- مرتب‌سازی صعودی بر اساس تاریخ جلسه (نمای زمانی)، سقف ۶۰ ردیف.

### رابط کاربری

کارت «نمای جلسه‌های زوجی» در ستون کنار پرونده: جدول تاریخ / شماره و مدت /
طرف (همین مراجع یا پارتنر) / وضعیت / مشترک، با تأکید روی ردیف‌های مشترک.

## ۳. آنچه عمداً انجام نشد

- **ادغام یادداشت‌های دو پرونده** — نقض محرمانگی و مالکیت داده؛ پروندهٔ هر
  مراجع مستقل می‌ماند.
- **ساخت جلسهٔ مشترک خودکار برای هر دو پرونده** — یک جلسه در یک پرونده ثبت
  می‌شود و با پرچم مشترک علامت می‌خورد؛ کپی خودکار یعنی دو منبع حقیقت.
- **نمایش نام درمانگر جلسهٔ طرف مقابل** — برای کاهش افشا، فقط طرف و زمان.

## ۴. تأییدها و محدودیت‌ها

انجام‌شده:

- پارسر PHP (`php-parser`، `suppressErrors: false`) روی فایل‌های تغییریافته.
- بازبینی: کوئری نمای زوجی فقط `pas_cf_notes` و فقط ستون‌های غیرحساس.
- بازبینی: نمایش جلسه‌های پارتنر مشروط به `current_user_can_access_case`.
- `unzip -t` روی بستهٔ ساخته‌شده.

انجام‌نشده (محدودیت محیط): PHP CLI، وردپرس و MySQL در دسترس نیستند، بنابراین
این‌ها **تست نشده‌اند**:

- افزودن ستون `is_joint` با dbDelta روی دادهٔ موجود.
- ثبت/ویرایش جلسه با تیک مشترک و نمایش نشان آن.
- نمای زوجی در سه حالت: دسترسی به هر دو پرونده، دسترسی فقط به یکی، بدون لینک.
- ترتیب زمانی و نمایش شمسی تاریخ‌ها در جدول.

## ۵. نقطهٔ بازگشت

- فقط یک ستون افزایشی با پیش‌فرض ۰؛ بازگشت به 1.13.0 بدون حذف ستون کار
  می‌کند و کد قدیمی آن را نمی‌بیند.
- نمای زوجی کاملاً فقط‌خواندنی است؛ حذف آن هیچ داده‌ای را تغییر نمی‌دهد.
- پیش از نصب در محیط واقعی: پشتیبان دیتابیس + به‌روزرسانی فقط این افزونه.

## ۶. گام بعدی پیشنهادی — فاز ۷

از طریق پل پیامک/ایمیل موجود، با رضایت صریح مراجع و بدون ذخیرهٔ داده در
افزونهٔ دیگری.
