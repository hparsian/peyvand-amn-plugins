## ۳. معماری فعلی (چیزهایی که باید حفظ شوند)

- **توکن‌محور ولی ناقص:** `tokens.css` تعریف شده و `Pas_Core_Tokens::handle()` به‌عنوان
  dependency در ۸ افزونه استفاده می‌شود؛ اما پالت آن **آبی** است (`#2563eb`) و با
  پالت برند جدید فاز ۱۲ (`#B8ADA0`, `#F4F0E8`, `#51483F`, `#C8B48A`) هم‌خوان نیست.
- **فونت:** `Pas_Core_Fonts` ثبت می‌شود ولی **فایل‌های `.woff2` در مخزن نیستند**
  (فقط `vazirmatn.css` با آدرس نسبی) → عملاً فونت سفارشی لود نمی‌شود و مرورگر به
  Tahoma برمی‌گردد. دو افزونه هم موازی از Google Fonts استفاده می‌کنند.
- **HTML سمت سرور + هیدریت REST:** پنل مراجع با `render()` قالب خالی می‌دهد و
  `panel.js` با `GET /zdp/v1/panel-state` محتوا را می‌گیرد (دفاع در برابر کش).
  **هر بازطراحی باید همین قرارداد را نگه دارد** (نشتی داده/بایپس ورود ممنوع).
- **قرارداد انتخابگرها:** `panel.js` به IDهای ثابت وابسته است:
  `#zdp-panel-app`, `#zdp-mobile`, `#zdp-email`, `#zdp-otp`, `#zdp-otp-step`,
  `#zdp-mobile-step`, `#zdp-email-step`, `#zdp-send-otp-btn`, `#zdp-verify-otp-btn`,
  `#zdp-resend-otp-btn`, `#zdp-change-mobile-btn`, `#zdp-otp-timer`,
  `#zdp-login-message`, `.zdp-tab[data-tab]`, `.zdp-tab-panel[data-panel]`.
  تغییر نام این‌ها = شکستن ورود؛ طرح جدید فقط **ظاهر** را عوض می‌کند.
- **دسترسی مرکزی:** همهٔ صفحات مدیریتی از کپابیلیتی‌های `Pas_Core_*` استفاده می‌کنند
  (`PAS_CF_CAP`, `manage_options`, ...). بازطراحی نباید هیچ چک دسترسی را جابه‌جا کند.
- **پیشوندگذاری CSS خوب است:** ۹۹٪ انتخابگرها پیشوند اختصاصی دارند؛ فقط دو قاعدهٔ
  `body.zdp-panel-blank` و `body.psy-exam-standalone-body` سراسری‌اند و هر دو به
  کلاس body محدودند → ریسک تداخل با Astra/Elementor پایین است.

## ۵. قراردادهایی که بازطراحی نباید بشکند

1. **احراز هویت/OTP/رمزنگاری:** هیچ تغییری در `class-otp-auth.php`, `Login_Service`,
   `Pas_Core_Crypto`, نرخ‌محدودیت‌ها، TTL و قفل تلاش‌ها. UI فقط لایهٔ نمایش است.
2. **IDها و data-attributeهای `panel.js`** (فهرست بخش ۳) و `data-tab`/`data-panel`.
3. **REST/AJAX:** نام routeها، nonce (`wp_rest`)، ساختار پاسخ `{success, data:{...}}`.
4. **دسترسی:** هیچ صفحه/دکمه‌ای بدون همان کپابیلیتی قبلی باز نشود؛ و هیچ صفحه‌ای که
   قبلاً بسته بود با «طراحی زیبا» باز نشود.
5. **کش:** قالب خالی + هیدریت REST حفظ شود؛ CSS/JS جدید نباید داده‌ی شخصی در HTML
   اولیه بگذارد.
6. **پیشوندگذاری CSS:** همهٔ استایل‌های جدید با پیشوند `pui-` و بدون قاعدهٔ سراسری
   روی `html/body` (به‌جز صفحهٔ ورود/پنل که کل صفحه مالِ ماست).
7. **بدون build step اجباری:** پروژه امروز CSS/JS خام سرو می‌کند؛ UI Kit هم باید
   خام و نسخه‌دار باشد (مینیفای اختیاری، نه لازم).

## ۶. ریسک تداخل با قالب/صفحه‌ساز

- استایل‌ها پیشوند دارند → تداخل پایین.
- تنها ریسک‌های واقعی: (الف) `:root` مشترک برای متغیرها (بی‌خطر)، (ب) اگر UI Kit
  فونتی سراسری روی `body` اعمال کند (**نباید بکند**؛ فقط در پوسته‌های اختصاصی)،
  (ج) بارگذاری کتابخانه‌ای که خودش روی `document` شنونده می‌گذارد (ApexCharts فقط در
  صفحات نمودار و با namespace).
- راهکار: CSS در `@layer pui.tokens, pui.base, pui.components, pui.utilities` و
  استایل‌های صفحه‌محور با کلاس ریشه‌ای `.pui-shell`.

## ۸. جمع‌بندی ممیزی

اکوسیستم از نظر **منطق و امنیت** بالغ است (فاز ۱۱)، ولی از نظر **زبان بصری**
چهار محصول جدا با دو پالت، فونت ناکارآمد، بدون دارک‌مود کنترل‌شده، بدون مرکز
مانیتورینگ و بدون نمودار است. کار فاز ۱۲ سه لایه دارد:

1. **UI Kit مرکزی** (`payvand-amn-ui-kit`) که پالت برند، فونت، کامپوننت‌ها و دارک‌مود
   را یک‌جا و بدون بار سراسری تعریف کند.
2. **بازطراحی چهار محیط** با حفظ قراردادهای بخش ۵.
3. **لایهٔ کیفیت**: Playwright (اسکرین‌شات/دسترس‌پذیری/رگرسیون) + بررسی کنسول و PHP.

طرح پیشنهادی در [`docs/phase12-design-proposal.md`](phase12-design-proposal.md) است.
