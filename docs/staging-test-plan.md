# چک‌لیست تست staging — پیوند امن (فازهای ۰ تا ۸)

این سند برای اجرای دستی در یک **کلون staging** از سایت واقعی نوشته شده است.
هیچ‌کدام از فازها در محیط توسعه اجرا نشده‌اند (PHP CLI/وردپرس/MySQL در دسترس
نبود)؛ بنابراین این چک‌لیست اولین تأیید واقعی رفتار است.

## ۰. پیش‌نیازها (قبل از هر نصبی)

- [ ] کلون staging از دیتابیس و `wp-content` گرفته شده و **روی staging** قابل
      بازگردانی است.
- [ ] از دیتابیس یک `mysqldump` تازه گرفته شده و مسیرش ثبت شده:
      `mysqldump ... > pre-phase-test-YYYYMMDD.sql`
- [ ] از `wp-content/plugins/pivand-amn-*` و `wp-content/pas-encryption-key.php`
      نسخهٔ فایل‌محور گرفته شده.
- [ ] نسخه‌های فعلی هر افزونه یادداشت شده (پیش از نصب).
- [ ] PHP 8.1+ و WordPress 6.6+ تأیید شده.
- [ ] مشخص است کلید رمزنگاری از `wp-config.php` می‌آید یا از
      `wp-content/pas-encryption-key.php` (در صفحهٔ «زیرساخت پیوند امن» دیده
      می‌شود). **کلید را جایی کپی/چاپ نکن.**

خط پایه (baseline) را ثبت کن تا بعداً بشود مقایسه کرد:

```sql
SELECT COUNT(*) FROM wp_pas_cf_cases;
SELECT COUNT(*) FROM wp_pas_cf_notes;
SELECT COUNT(*) FROM wp_psy_attempts;
SELECT COUNT(*) FROM wp_zdp_intake;
SHOW COLUMNS FROM wp_pas_cf_cases;
SHOW COLUMNS FROM wp_pas_cf_notes;
```

## ۲. فاز ۰ — ایمن‌سازی

- [ ] در کد پل پیامک هیچ اعتبارنامهٔ هاردکدشده باقی نمانده

- [ ] صفحهٔ پل پیامک منبع اعتبارنامه را نشان می‌دهد
      (`credentials_source()`): wp-config یا آپشن.
- [ ] اگر رمز چرخیده، `uses_leaked_credentials()` روی «لو‌رفته نیست» است؛ اگر

- [ ] بخش «سنجش داده‌های رمزنگاری‌شده» اعداد را نشان می‌دهد و صفحه کند نیست.
- [ ] نصب افزونه‌های قدیمی (1.1.5 پل پیامک) رفتار را نمی‌شکند.

## ۳. فاز ۱ — رجیستری هویت

- [ ] سه جدول `wp_pas_clients`، `wp_pas_client_identifiers`،

- [ ] دکمهٔ «بازسازی» کار می‌کند و تعداد کلاینت‌ها منطقی است

- [ ] بخش «رجیستری هویت مراجع» بدون خطا باز می‌شود.
- [ ] هیچ داده‌ای در جدول‌های افزونه‌های دیگر تغییر نکرده (اعداد baseline).

      تغییر نکرده** است.
- [ ] دکمهٔ انتقال بدون تیک بازنویسی فقط فیلدهای خالی را پر می‌کند.
- [ ] با تیک بازنویسی، فیلد اختلاف‌دار عوض می‌شود و ردیف منبع در

- [ ] باکس «تایم‌لاین پرونده» رویدادها را نزولی نشان می‌دهد و «انتقال فرم»

- [ ] فهرست «پرونده‌های راکد» با پرونده‌ای که آخرین جلسه‌اش قدیمی است هم‌خوان

      مربوطه حذف می‌شوند).

## ۱۱. بازگشت (rollback)

هر فاز فقط افزایشی است، ولی برای اطمینان:

1. **بازگشت افزونه**: بستهٔ نسخهٔ قبلی را از پوشهٔ پشتیبان روی همان پوشه
   بازگردان. ستون‌ها/جدول‌های جدید بدون آسیب می‌مانند (کد قدیمی آن‌ها را
   نمی‌بیند).
2. **بازگشت دیتابیس**: فقط اگر داده هم باید برگردد —
   `mysql ... < pre-phase-test-YYYYMMDD.sql`.
3. **یادآور**: برای توقف فوری، کانال هر پرونده را «بدون یادآور» کن یا تیک
   رضایت را بردار؛ هیچ ارسال خودکاری وجود ندارد.
4. بعد از بازگشت، `wp-content/debug.log` را دوباره چک کن.

## ۱۱.۱. سناریوی سرتاسری اکوسیستم (اجباری)

پس از نصب و پیکربندی، یک دور کامل مسیر مراجع را اجرا کن. سناریو و انتظارات
هر گام در `docs/ecosystem-scenario.md` است و اسکریپت اجراکننده در
`tests/ecosystem-scenario.php`:

```bash
php wp-cli.phar --path=. --allow-root eval-file tests/ecosystem-scenario.php
```

- [ ] خروجی با `TOTALS: {"PASS":17}` تمام شد (بدون FAIL/BLOCKED).
- [ ] `wpdb last_error: none` بود.
- [ ] در `debug.log` هیچ نوتیس/وارنینگ تازه‌ای ثبت نشد.
- [ ] پنل مراجع و پرونده در مرورگر همان داده‌ای را نشان می‌دهند که اسکریپت
      گزارش کرد (نام، سن، جلسه، نتیجهٔ آزمون).
- [ ] گزارش مدیر فقط دادهٔ staging را نشان می‌دهد (هیچ ردیف واقعی وارد نشده).

## ۱۲. محدودیت‌های این چک‌لیست

- هیچ تست خودکار (PHPUnit/Playwright) در مخزن نیست؛ همه‌چیز دستی است.
- ارسال پیامک به الگوی تأییدشده در ملی‌پیامک و ارسال ایمیل به SMTP سالم سایت
  وابسته است؛ اگر این‌ها در staging نیستند، آن دو مورد را «تست‌نشده» علامت
  بزن، نه «قبول».
- `wp_mail` در staging معمولاً به بیرون ارسال نمی‌کند؛ از یک افزونهٔ لاگ ایمیل
  یا صندوق تست استفاده کن.
