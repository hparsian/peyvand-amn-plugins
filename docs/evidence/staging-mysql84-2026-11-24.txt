شاهد خام آزمون استیجینگ روی Oracle MySQL 8.4 واقعی — ۲۰۲۶-۱۱-۲۴
================================================================

این فایل نتیجهٔ اجرای امروز روی یک سرور واقعی **Oracle MySQL Community Server
8.4.11** (نه MariaDB و نه drop-in شبیه‌ساز SQLite) است. همان مجموعهٔ suiteهایی
اجرا شد که پیش‌تر روی SQLite و MariaDB 11.4.5 اجرا شده بود، با همان runner.
هیچ خط PASS/FAIL از اجرای قبلی بازنویسی یا ادعاشده نشده است؛ لاگ کامل خام در
`staging-mysql84-2026-11-24-raw.txt` (۴۴۱ خط، SHA-256
`4892e28cafca1b5f500d59530804afaefb7597c0eadb938b5ee62c7b61b13c6f`) و CSV
واقعی export در `staging-mysql84-2026-11-24-export.csv` (۱۵۵ بایت، SHA-256
`675f1228ae7337349597624c6843226617bb7b4de5ab89839b03dd8ae17dd20e`) کنار
همین فایل است.

این اجرا آخرین شکاف دیتابیس را می‌بندد: پیش از این فقط MariaDB آزموده شده بود و
خودِ شاهد MariaDB، «Oracle MySQL 8.0/8.4 آزموده نشد» را در فهرست اجرانشده‌ها
داشت.

## چطور سرور بالا آمد

میزبان استیجینگ واقعی پروژه همچنان در دسترس نبود و دسترسی root هم ندارد
(`sudo`: «no new privileges»؛ سوکت Docker: permission denied). بنابراین خودِ
سرور MySQL به‌صورت unprivileged از بستهٔ رسمی باینری راه افتاد:

| مورد | مقدار |
|---|---|
| سرور | `8.4.11` — MySQL Community Server - GPL، بیلد رسمی `linux-glibc2.28 x86_64 minimal` از `cdn.mysql.com/archives/mysql-8.4/` |
| راه‌اندازی | `mysqld --initialize-insecure` سپس `mysqld` با کاربر عادی، دیتادیر `/tmp/mysql84/data`، سوکت `/tmp/mysql84/mysql.sock`، `127.0.0.1:3308` |
| کتابخانه‌های جانبی | `libaio1t64` و `libnuma1` با `dpkg-deb -x` در پوشهٔ محلی (بدون نصب سیستم) و `LD_LIBRARY_PATH` |
| موتور ذخیره‌سازی | InnoDB (`@@default_storage_engine = InnoDB`) |
| دیتابیس | `wp_pas` — `utf8mb4` / `utf8mb4_unicode_ci` |
| sql_mode | `ONLY_FULL_GROUP_BY,STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION` |
| PHP | 8.3.32 (static-php-cli **bulk**: mysqli/mysqlnd/pdo_mysql) |
| WordPress | 7.1.5 |
| WP-CLI | 2.12.0 |
| کلاینت MySQL | 8.4.11 (`mysql`/`mysqldump` رسمی همان بسته) |
| WP_DEBUG | روشن، `WP_DEBUG_LOG` روشن، `WP_DEBUG_DISPLAY` خاموش |

`sql_mode` اینجا از MariaDB سخت‌گیرانه‌تر است: `ONLY_FULL_GROUP_BY` و
`NO_ZERO_DATE`/`NO_ZERO_IN_DATE` هم فعال‌اند. suiteها با همین حالت اجرا شدند.

خروجی واقعی تأیید موتور:

```
version  comment                      engine
8.4.11   MySQL Community Server - GPL InnoDB
```

```
Database  Create Database
wp_pas    CREATE DATABASE `wp_pas` /*!40100 DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci */ /*!80016 DEFAULT ENCRYPTION='N' */
```

## چیزهایی که فقط روی این MySQL واقعی دیده می‌شوند

- `information_schema.TABLES` نشان می‌دهد هر ۱۲ جدول `wp_pas_*` روی InnoDB و با
  `utf8mb4_unicode_520_ci` ساخته شده‌اند (در ۳۹ جدول کل دیتابیس):

```
TABLE_NAME                      ENGINE  TABLE_COLLATION
wp_pas_cf_audit_log             InnoDB  utf8mb4_unicode_520_ci
wp_pas_cf_cases                 InnoDB  utf8mb4_unicode_520_ci
wp_pas_cf_note_history          InnoDB  utf8mb4_unicode_520_ci
wp_pas_cf_notes                 InnoDB  utf8mb4_unicode_520_ci
wp_pas_client_identifiers       InnoDB  utf8mb4_unicode_520_ci
wp_pas_clients                  InnoDB  utf8mb4_unicode_520_ci
wp_pas_dashboard_audit          InnoDB  utf8mb4_unicode_520_ci
wp_pas_dashboard_notifications  InnoDB  utf8mb4_unicode_520_ci
wp_pas_field_maps               InnoDB  utf8mb4_unicode_520_ci
wp_pas_field_provenance         InnoDB  utf8mb4_unicode_520_ci
wp_pas_identity_conflicts       InnoDB  utf8mb4_unicode_520_ci
wp_pas_sms_log                  InnoDB  utf8mb4_unicode_520_ci
```

- نام قراردادی ممیزی با نقطه روی MySQL 8.4 هم سالم می‌ماند؛ ردیف واقعی جدول
  `wp_pas_dashboard_audit` پس از suite export:

```
id  action        result
1   export.cases  ok
```

- جدول `wp_pas_cf_audit_log` در همین اجرا ۳۲ ردیف گرفت و اکشن‌ها با نام
  قراردادی خود ثبت شدند: `add_note` ۷، `create` ۱۳، `edit_case` ۴،
  `delete_note` ۳، `edit_note` ۲، `restore_note` ۱، `apply_intake_map` ۱،
  `send_reminder` ۱. ستون‌های این جدول (`id`, `case_id`, `user_id`, `action`,
  `ip`, `created_at`) روی MySQL بدون خطا ساخته شدند.
- کوئری‌های اسکیمای داشبورد و `SHOW COLUMNS`/`information_schema` روی MySQL 8.4
  با `ONLY_FULL_GROUP_BY` بدون خطا اجرا شدند و در سناریوی سرتاسری
  `wpdb last_error: none` ثبت شد.
- PHP این اجرا بیلد **bulk** است تا `mysqli` واقعی وجود داشته باشد؛ بیلد common
  فقط `pdo_mysql`/`mysqlnd` دارد و وردپرس با آن بالا نمی‌آید.

## debug.log و لاگ سرور (بدون لاپوشانی)

برخلاف اجرای MariaDB، این‌بار `wp-content/debug.log` ساخته شد: ۴۵۸ بایت با
**یک** ردیف هشدار، و آن هم از هستهٔ وردپرس است نه از بسته‌های پروژه:

```
[24-Nov-2026 18:36:20 UTC] PHP Warning:  wp_update_themes(): An unexpected error
occurred. Something may be wrong with WordPress.org or this server's
configuration. ... (WordPress could not establish a secure connection to
WordPress.org. ...) in /tmp/wp-mysql84/wp-includes/functions.php on line 6260
```

این ردیف از بررسی به‌روزرسانی پوسته‌ها (`wp_update_themes`) می‌آید و علتش
نداشتن دسترسی خروجی HTTPS به `wordpress.org` در این سندباکس است؛ هیچ فایل پروژه
و هیچ افزونه‌ای در آن دخیل نیست و هیچ notice/warning دیگری (از جمله هشدار
«Translation loading … too early») ثبت نشده است.

لاگ خطای سرور MySQL فقط سه `[Warning]` زمان راه‌اندازی دارد (پیکربندی خودِ
سرور، نه خطای اجرا) و **هیچ `[ERROR]`**ی در طول suiteها ندارد:

```
[Warning] [MY-010097] Insecure configuration for --secure-file-priv ...
[Warning] [MY-010068] CA certificate ca.pem is self signed.
[Warning] [MY-011810] Insecure configuration for --pid-file: Location '/tmp' ...
```

## اجرا نشد (نباید «قبول» شمرده شود)

- **میزبان استیجینگ واقعی پروژه** — این اجرا یک سرور MySQL محلی و تازه بود،
  نه کلون سایت واقعی با داده و افزونه‌های همان میزبان.
- **Oracle MySQL 8.0** — نسخهٔ ۸.۴ آزموده شد؛ ۸.۰ (پایان پشتیبانی) آزموده نشد.
- مرورگر، چیدمان RTL، جریان ۳۶۰px و بررسی بصری داشبورد.
- ارسال واقعی پیامک و ایمیل (فقط مسیر کد، صف و علامت‌گذاری بررسی شد).
- اسکریپت‌های HTTP فاز ۱۱ (`tests/phase11/*.php`) چون وب‌سرور محلی بالا نیامد؛
  `migration-verify` افزون بر آن به نصب نسخهٔ قدیمی داشبورد نیاز دارد.
- به‌روزرسانی واقعی از گیت‌هاب (نیازمند توکن و ترافیک به مخزن).

## برای اجرا روی میزبان استیجینگ واقعی چه چیزی لازم است

۱. دسترسی اجرای دستور روی همان میزبان (SSH یا کنسول پنل) با کاربری که
   `wp`/`php` دارد، به‌همراه `WP-CLI` و `mysqli`.
۲. یک **کلون staging** از دیتابیس و `wp-content` که بازگردانی‌اش آزموده شده
   باشد، و `mysqldump` تازه پیش از شروع.
۳. اجازهٔ نصب ۱۲ بستهٔ `dist/` از پنل یا `wp plugin install` (روی میزبان‌هایی
   که `DISALLOW_FILE_MODS` دارند این کار از پیشخوان ممکن نیست).
۴. کلید رمزنگاری موجود روی همان سایت (`wp-config.php` یا
   `wp-content/pas-encryption-key.php`) — بدون چاپ کردن مقدارش.
۵. اگر ارسال واقعی پیامک/ایمیل هم لازم است: الگوی تأییدشدهٔ ملی‌پیامک و یک
   SMTP سالم روی همان staging.
۶. برای فاز ۱۱: یک وب‌سرور محلی روی همان میزبان که اسکریپت‌های HTTP را اجرا
   کند، و برای `migration-verify` یک نسخهٔ قدیمی داشبورد (۱.۹.۰) برای ارتقا.
