# سناریوی کامل اکوسیستم — مسیر سرتاسری یک مراجع

این سند یک سناریوی کامل و **قابل تکرار** از اکوسیستم پیوند امن است: مسیر یک
مراجع از اولین تماس عمومی تا پروندهٔ بالینی، آزمون، جلسهٔ زوجی، یادآور، مرز
دسترسی و گزارش‌ها؛ همراه با نقش هر افزونه، جدول‌هایی که نوشته می‌شوند و
کنترل‌های امنیتی هر گام.

اسکریپت اجراکننده: `tests/ecosystem-scenario.php`
خروجی خام اجرا: `docs/evidence/ecosystem-scenario-run.txt`

## ۰. خلاصهٔ اجرا

| مورد | نتیجه |
|---|---|
| گام‌های سناریو | **۱۷** |
| PASS | **۱۷** (در دو اجرای پشت‌سرهم) |
| FAIL / BLOCKED | ۰ / ۰ |
| `wpdb->last_error` | none |
| محیط | WordPress 7.1.4 · PHP 8.5.8 · SQLite drop-in · ۱۰ افزونه فعال |

## ۱. بازیگران و نقش‌ها

| بازیگر | نقش وردپرس | چه می‌بیند |
|---|---|---|
| بازدیدکننده | مهمان | فرم تماس (`payvand_contact`)، ویجت نوبت (`zdp_booking_widget`)، آزمون عمومی (`psy_exam`)، فید (`piwand_feed`) |
| مراجع | `subscriber` با ورود OTP | تب‌های پنل: نوبت، فرم ارزیابی، پیام، آزمون‌ها |
| درمانگر | `pas_cf_therapist` | فقط پرونده‌های ارجاع‌شده به خودش |
| مدیر | `administrator` | همه‌چیز + داشبورد سلامت/انطباق + 2FA |
| سرویس‌ها | ملی‌پیامک / SMTP | پیامک و ایمیل از یک نقطهٔ اتصال (پل) |

## ۲. سناریو، گام به گام

هر گام: **چه کسی** → **چه کاری** → **چه چیزی نوشته می‌شود** → **کنترل** →
**نتیجهٔ اجرای واقعی**.

### گام ۱ — اولین تماس از سایت عمومی
بازدیدکننده فرم «تماس با ما» را پر می‌کند (نام، موبایل، نوع مراجعه، نوع
مشاوره، متن، تیک حریم خصوصی).

- می‌نویسد: `payvand_messages`
- کنترل: nonce AJAX (`check_ajax_referer`) + rate limit بر اساس IP + sanitize
  + اعتبارسنجی مقادیر مجاز (`visit_type`/`consult_type`)
- اجرا: ارسال با nonce واقعی → `{"success":true}` و ثبت ردیف؛ ارسال بدون
  nonce → پاسخ `-1` (رد شد).

### گام ۲ — ساخت ایندکس هویت
مدیر/کران رجیستری هویت را بازسازی می‌کند تا همان شماره در همهٔ کانال‌ها یک
«مراجع» واحد باشد.

- می‌نویسد: `pas_clients`، `pas_client_identifiers`، `pas_identity_conflicts`
- منبع: `pas_cf_cases`، `psy_invitations`، `zdp_leads`، `payvand_messages`
- اجرا: `rebuild()` بدون خطا؛ شمارش مراجعان رشد کرد (۳ → ۲۱ در سه اجرا).

### گام ۳ — ورود مراجع با OTP و پر کردن فرم ارزیابی
مراجع شماره را وارد می‌کند؛ پنل کاربر می‌سازد (`user_login = zdp_<موبایل>`)
و فرم ارزیابی را پر می‌کند.

- می‌نویسد: `wp_users`، usermeta (`zdp_mobile`, `zdp_full_name`)، `zdp_intake`
- کنترل: کد ۵ دقیقه‌ای + شمارش تلاش + rate limit؛ محتوای فرم با
  `Pas_Core_Crypto` رمزنگاری می‌شود (`payload_encrypted=1`)
- اجرا: `encrypted=yes`، خواندن از مسیر رسمی `zdp_get_intake_for_phone`
  موفق (`filter_read=yes`) و نام برگشتی درست.

### گام ۴ — رزرو نوبت
مراجع از پنل نوبت می‌گیرد.

- می‌نویسد: `zdp_bookings`
- کنترل: قیمت و نام خدمت از سمت سرور (نه از کلاینت)، قفل بازهٔ زمانی،
  اعتبارسنجی ساعات کاری، rate limit رزرو
- اجرا: `booking id=4 status=در انتظار تایید واریز slot=2026-11-25 13:00`.
  نکته: در اجرای اول این گام به‌درستی با «این بازه رزرو شده است» رد شد
  (اسکریپت بازهٔ ثابت داشت) — یعنی کنترل هم‌زمانی کار می‌کند؛ سپس اسکریپت
  بازهٔ تصادفی گرفت و رزرو ثبت شد.

### گام ۵ — باز شدن پرونده توسط درمانگر
درمانگر پروندهٔ بالینی را برای همان موبایل می‌سازد.

- می‌نویسد: `pas_cf_cases` (هویت + مالکیت + وضعیت) و `pas_cf_audit_log`
- اجرا: `case_id=18 owner=1 therapist=1`.

### گام ۶ — نگاشت فرم ارزیابی به پرونده
درمانگر پیش‌نمایش نگاشت را می‌بیند (fill / same / conflict) و تأیید می‌کند.

- می‌نویسد: `pas_cf_cases` (فیلدهای عمومی + فیلدهای `*_encrypted`) و
  `pas_field_provenance` برای هر فیلد
- کنترل: فیلدهای بالینی فقط با کلید رمزنگاری نوشته می‌شوند؛ تاریخ شمسی
  تبدیل می‌شود؛ منبع هر فیلد ثبت می‌شود
- اجرا: `preview_rows=15 fill=13 updated=13`، `age=32`، `marital=متاهل`،
  `provenance=13`، `intake_submitted_at` ثبت شد.

### گام ۷ — ثبت جلسه
درمانگر یادداشت جلسه را می‌نویسد (مدت، وضعیت، جلسهٔ بعد).

- می‌نویسد: `pas_cf_notes` (`content_encrypted`) + `pas_cf_note_history` در
  ویرایش‌ها
- اجرا: `note_id=35` و متن پس از رمزگشایی **دقیقاً** همان ورودی بود.

### گام ۸ — تایم‌لاین پرونده
- اجرا: ۴ رویداد با انواع `case_created`, `intake_received`, `intake_mapped`,
  `session` — ترتیب درست.

### گام ۹ — آزمون روان‌سنجی (CSI-16)
درمانگر دعوت می‌فرستد؛ مراجع از لینک عمومی پاسخ می‌دهد؛ نتیجه در پرونده دیده
می‌شود.

- می‌نویسد: `psy_invitations` (توکن ۴۰ کاراکتری) → `psy_attempts`
  (`result_data` رمزنگاری‌شده)
- کنترل: توکن یک‌بارمصرف + `claim()` اتمیک + rate limit + اعتبارسنجی شناسهٔ
  سؤال‌ها
- اجرا: دعوت ساخته شد، `POST /psy/v1/submit` با ۱۶ پاسخ → HTTP 200، سپس
  `Pas_CF_Case_File::get_assessment_scores($phone)` نتیجه را از طریق فیلتر
  `psy_get_assessment_scores_for_phone` برگرداند (بدون خواندن مستقیم جدول
  `psy_*`).

### گام ۱۰ — نمای زوجی
پروندهٔ همسر با `partner_phone` ساخته می‌شود و جلسهٔ مشترک ثبت می‌شود.

- اجرا: `partner_linked=yes`، `joint_sessions=3`؛ نمایش فقط متادیتا و مشروط
  به دسترسی به **هر دو** پرونده.

### گام ۱۱ — یادآور جلسه
درمانگر یادآور را فعال می‌کند (رضایت + کانال).

- کنترل: بدون رضایت ارسال نمی‌شود (`no_consent`)، بدون جلسهٔ بعدی
  (`no_session`)، بدون کانال (`no_channel`)، با فاصلهٔ ۱۲ ساعت (`cooldown`)
- اجرا: `blocker=ok`، ارسال از فیلتر `pas_send_sms` به پل پیامک،
  `pas_sms_log` از ۷ به ۸ رسید و `reminder_last_sent_at` ثبت شد.
  (پیامک واقعی ارسال نشد چون اعتبارنامهٔ ملی‌پیامک در محیط تست نیست؛
  رفتار درگاه/لاگ تأیید شد.)

### گام ۱۲ — مرز دسترسی
درمانگر دوم فقط پروندهٔ خودش را می‌بیند.

- کنترل: تک‌منبع `Pas_CF_Security` در PHP و SQL
- اجرا: `own=true other=false list=1 therapist_cases=1 admin_cases=23` —
  هم چک تکی و هم scope گزارش‌ها و فهرست، همان قانون را رعایت کردند.

### گام ۱۳ — گزارش‌های مدیریتی
- اجرا: `summary()` بدون نوتیس (باگ `prepare` که در بازبینی رفع شد)، کلیدهای
  `cases_total`، `cases_active`، `cases_by_status` سالم.

### گام ۱۴ — امنیت حساب مدیر (2FA)
- اجرا: TOTP با کد محاسبه‌شدهٔ همان پنجرهٔ زمانی **پذیرفته** شد؛ کد پشتیبان
  یک‌بار مصرف شد و استفادهٔ دوباره **رد** شد؛ ۹ کد باقی ماند.

### گام ۱۵ — سلامت اکوسیستم و انطباق
- اجرا: `plugins=4` (آن‌هایی که هسته می‌شناسد)، ۰ مورد missing/inactive،
  ۷ بررسی انطباق: ۵ ok و ۲ warn (هشدارهای پیکربندی، نه خطا).

### گام ۱۶ — صف تولید محتوا
- اجرا: `ACO_Queue::enqueue()` ردیف ساخت (`queued_id=6`)، شمارش‌ها
  `pending/processing/done/failed` درست. (تولید خودکار محتوا نیازمند کلید
  سرویس هوش مصنوعی است و در این محیط اجرا نشد.)

### گام ۱۷ — فید روزانه
- اجرا: شورت‌کد `[piwand_feed]` رندر شد (`html_bytes=5857`، ۳۰ کارت، بدون
  حالت خالی).

## ۳. آنچه این سناریو اثبات می‌کند

1. **جریان داده بین ۱۰ افزونه** بدون خطا و بدون `wpdb->last_error` کار می‌کند:
   تماس → هویت → پنل → پرونده → آزمون → گزارش → پیامک → فید.
2. **رمزنگاری** در سه نقطه (فرم ارزیابی، یادداشت جلسه، نتیجهٔ آزمون) رفت و
   برگشت؛ محتوای خام در دیتابیس ذخیره نمی‌شود.
3. **قراردادهای فیلتر** (`zdp_get_intake_for_phone`،
   `psy_get_assessment_scores_for_phone`، `pas_send_sms`) مصرف‌کنندهٔ واقعی
   دارند و رفتارشان در اجرا درست است.
4. **مرز دسترسی** هم در کوئری، هم در فهرست و هم در گزارش‌ها یکسان اعمال
   می‌شود (تک‌منبع، بدون کپی محلی).
5. **کنترل‌های ضد سوءاستفاده** در ورودی عمومی (nonce، rate limit، اعتبارسنجی
   مقادیر مجاز) و در ورودی نوبت (قیمت سمت سرور، قفل بازه) واقعاً فعال‌اند.

## ۴. محدودیت‌های صریح این اجرا

| مورد | وضعیت |
|---|---|
| ارسال واقعی پیامک/ایمیل | فقط تا مرز پل و لاگ؛ بدون اعتبارنامهٔ بیرونی |
| تولید واقعی محتوا با AI | فقط صف؛ نیازمند کلید سرویس |
| درگاه پرداخت زرین‌پال | فقط مسیر «کارت‌به‌کارت»؛ درگاه پیکربندی نشده |
| تست مرورگری (کوکی/JS) | انجام نشد؛ همهٔ گام‌ها از API/PHP اجرا شدند |
| MySQL واقعی | اجرا روی SQLite؛ `GET_LOCK` در این درایور جواب داد ولی رفتار قفل هم‌زمانی MySQL تأیید نشد |
| 2FA روی فرم ورود | فقط هستهٔ TOTP و کدهای پشتیبان؛ چالش ورود مرورگری تست نشد |

## ۵. اجرای مجدد

```bash
# پیش‌نیاز: یک وردپرس با ۱۰ افزونهٔ فعال و کلید رمزنگاری هسته
php wp-cli.phar --path=web --allow-root eval-file tests/ecosystem-scenario.php
```

اسکریپت خودبسنده است: هر بار شمارهٔ موبایل تازه می‌سازد، بازهٔ نوبت تصادفی
می‌گیرد و در پایان خلاصهٔ `{"PASS":17}` را چاپ می‌کند. اگر `wpdb->last_error`
غیرخالی یا هر گامی FAIL شود، اجرا قابل تشخیص است.
