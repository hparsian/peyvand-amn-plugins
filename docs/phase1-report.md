# فاز ۱ — رجیستری هویت مراجع (گزارش اجرا)

> **یادداشت فاز ۱۵ (۱۴۰۵/۰۸/۲۴):** بسته‌هایی که در این گزارش با مسیر `dist/` آمده‌اند بازنشسته و حذف شده‌اند؛ تنها بستهٔ رسمی و بازبینی‌شده، خروجی فاز ۱۵ در `release/v1/plugins/` است. متن زیر سابقهٔ تاریخی همان فاز است و دست‌نخورده مانده.

**وضعیت:** انجام شد — منتظر تأیید برای فاز ۲
**دامنه‌ی تغییر:** فقط افزونه‌ی هسته (`pivand-amn-core` 1.3.8 → **1.4.0**).
هیچ فایل دیگری از ۹ افزونه‌ی دیگر تغییر نکرد و **هیچ جدول موجودی تغییر نکرد**.

---

## ۱. چه چیزی ساخته شد

### ۱.۱ سه جدول جدید (افزایشی، `dbDelta`)

| جدول | نقش |
|---|---|
| `pas_clients` | یک ردیف برای هر «خوشه‌ی هویت»: `client_id` پایدار، نام نمایشی، موبایل/ایمیل اصلی، وضعیت (`active`/`review`)، تعداد تعارض، تعداد منبع |
| `pas_client_identifiers` | هر شناسه‌ی مشاهده‌شده: نوع، مقدار نرمال‌شده، منبع، شماره‌ی رکورد منبع، نام همان رکورد، `last_seen_at` |
| `pas_identity_conflicts` | تعارض‌های باز: نوع، شناسه، جزئیات (نام‌ها/تعداد)، زمان |

`client_id` قالب `pc_` + ۲۶ کاراکتر (ULID-like) دارد و در بازسازی‌های بعدی
**پایدار** می‌ماند: اگر هر شناسه‌ی عضو خوشه قبلاً به یک `client_id` نگاشت شده
بود، همان دوباره استفاده می‌شود.

### ۱.۲ کلاس `Pas_Core_Client_Registry`

- `install()` — ساخت/آپدیت idempotent جدول‌ها؛ روی فعال‌سازی و در صورت
  اختلاف `pas_core_db_version` روی `plugins_loaded` (اولویت ۴) اجرا می‌شود.
- `rebuild()` — فقط با کلیک ادمین. مراحل:
  1. خواندن ۵ منبع در دسته‌های ۵۰۰ ردیفی (سقف ۲۰٬۰۰۰ مشاهده؛ عبور از سقف =
     ایندکس ناقص و نمایش هشدار).
  2. خوشه‌بندی با union-find روی شناسه‌های یکسان.
  3. نگاشت به `client_id` (استفاده‌ی مجدد از شناسه‌ی موجود).
  4. ثبت شناسه‌ها با `INSERT ... ON DUPLICATE KEY UPDATE` (idempotent).
  5. تشخیص تعارض‌ها و ثبت آن‌ها.
  6. کنار گذاشتن ردیف‌هایی که این‌بار دیده نشدند (`last_seen_at` قدیمی) —
     فقط ردیف‌های خودکار؛ ردیف `source='manual'` آینده دست‌نخورده می‌ماند.
- `stats()` / `recent_conflicts()` / `sample_clients()` — فقط برای نمایش ادمین.
- `get_client()` / `get_client_by_identifier()` / `filter_get_client()` — برای
  مصرف‌کننده‌های آینده.

### ۱.۳ قرارداد `pas_get_client`

```php
apply_filters('pas_get_client', null, ['client_id' => 'pc_...']);
apply_filters('pas_get_client', null, ['type' => 'mobile', 'value' => '0912...']);
apply_filters('pas_get_client', null, ['wp_user_id' => 12]);
```

خروجی: `client_id`، نام نمایشی، وضعیت، تعداد تعارض، فهرست شناسه‌ها.
**هیچ داده‌ی بالینی در خروجی نیست** و فقط برای کاربر دارای `manage_options`
یا `PAS_CF_CAP` کار می‌کند. در `Pas_Core_Filter_Registry` ثبت شد.

### ۱.۴ رابط ادمین

پیشخوان → **«زیرساخت پیوند امن»** → بخش «رجیستری هویت مراجع»:
- وضعیت جداول، تعداد مراجعان، شناسه‌ها به تفکیک نوع، مراجعان «نیازمند بررسی»،
  تعارض‌های باز، زمان آخرین بازسازی.
- دکمه‌ی «بازسازی ایندکس هویت» (POST + nonce + `manage_options`).
- جدول تعارض‌های باز (حداکثر ۱۰۰) و نمونه‌ی ۳۰ مراجع با شناسه‌هایشان.

## ۳. قاعده‌ی هویت (بدون ادغام خودکار)

- اتصال **فقط** با شناسه‌ی یکسان: موبایل نرمال‌شده (`09xxxxxxxxx`)، ایمیل
  نرمال‌شده، یا `wp_user`.
- نام، نام خانوادگی، شماره‌ی همسر و آدرس **هرگز** باعث اتصال نمی‌شوند.
- موبایل هویت قطعی نیست. اگر یک شناسه بین چند نام / چند پرونده / چند حساب
  دیده شود، **ادغام نمی‌شود**؛ به‌جای آن تعارض ثبت می‌شود و مراجع وضعیت
  «نیازمند بررسی» می‌گیرد.

### انواع تعارض

| نوع | معنی |
|---|---|
| `shared_identifier` | یک شناسه برای ≥۲ نام مختلف (شماره‌ی مشترک یا ثبت اشتباه) |
| `multiple_wp_users` | ≥۲ حساب وردپرس با همین شناسه |
| `multiple_cases` | ≥۲ پرونده‌ی بالینی با همین شماره |
| `email_multiple_mobiles` | یک ایمیل با چند شماره (مثلاً تغییر شماره) — بررسی دستی |
| `missing_name` | شناسه‌ای که هیچ نامی برایش ثبت نشده (اطلاعاتی) |

**بررسی‌نشده (صادقانه):**
- **اجرای واقعی روی وردپرس/MySQL انجام نشد** — این محیط سایت زنده ندارد.
  بنابراین `dbDelta`، اجرای واقعی `rebuild()` و نمایش صفحه فقط از نظر نحوی و
  منطقی بررسی شده‌اند، نه با اجرای واقعی.
- **backfill واقعی روی داده‌ی شما اجرا نشد** (دیتابیس در دسترس نیست).
- آزمون بار روی دیتابیس بزرگ انجام نشد؛ سقف ۲۰٬۰۰۰ مشاهده و دسته‌های ۵۰۰تایی
  برای همین در نظر گرفته شده‌اند.

## ۵. نحوه‌ی استفاده

1. بسته‌ی `dist/pivand-amn-core-1.4.0.zip` را روی سایت جای‌گذاری کن.
   جداول جدید خودکار ساخته می‌شوند (بدون غیرفعال/فعال کردن).
2. پیشخوان → «زیرساخت پیوند امن» → «بازسازی ایندکس هویت» را یک‌بار بزن.
3. نتیجه را بخوان:
   - **مراجعان ایندکس‌شده** = تعداد خوشه‌های هویت.
   - **مراجعان نیازمند بررسی** = خوشه‌هایی که تعارض دارند (این‌ها همان
     مواردی هستند که باید دستی بررسی شوند؛ هیچ‌کدام ادغام نشده‌اند).
   - **شناسه‌ها به تفکیک نوع** = توزیع موبایل/ایمیل/حساب وردپرس.
4. جدول تعارض‌ها را ببین. اگر `shared_identifier` زیاد داشتی، یعنی شماره‌ها
   بین چند نفر مشترک‌اند یا ثبت اشتباه دارند — این دقیقاً همان چیزی است که
   نباید خودکار ادغام شود.

> اگر هشدار «ایندکس ناقص» دیدی، یعنی تعداد رکوردها از ۲۰٬۰۰۰ گذشته؛ در فاز ۲
> سقف را افزایش می‌دهیم یا backfill را دسته‌ای/زمان‌بندی‌شده می‌کنیم.

## ۶. محدودیت‌های شناخته‌شده (برای فازهای بعد)

1. **خوشه = «رکوردهایی که یک شناسه‌ی یکسان دارند»، نه اثبات یک انسان.**
   ادغام/تفکیک دستی (merge/split) در فاز ۲ به‌صورت UI کنترل‌شده اضافه می‌شود.
2. **ادغام خودکار حساب موبایل/ایمیل** وجود ندارد — طبق تصمیم فاز ۱.
3. **`pas_links`** (اتصال client به پرونده/نوبت/آزمون/نظرسنجی) عمداً در این
   فاز ساخته نشد؛ فاز ۲/۳.
4. **org-level dedupe ایمیل‌های هم‌شکل** (مثلاً `a+1@b.com`) انجام نمی‌شود.
5. **رجیستری روی cron خودکار اجرا نمی‌شود** — بازسازی دستی است تا رفتار
   غیرمنتظره نداشته باشیم.
